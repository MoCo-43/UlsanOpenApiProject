# 울산 OO배수지 3D 디지털 트윈 프로토타입

한일환경테크-산업용 Open API 데이터 기반 3D 디지털 트윈·AX 프로토타입

| 지원자 | A-2026-008 | |
| GitHub | `https://github.com/MoCo-43/UlsanOpenApiProject` | |

---

## 1. 프로젝트 개요

울산광역시를 대상으로 소규모 배수지의 3D 디지털 트윈 프로토타입을 구현했습니다.
공공 Open API를 실제로 연동해 원본 데이터를 수집하고, 공통 `SensorData`
구조로 표준화한 뒤, 3D로 표현한 배수지 설비에 연결해 이상징후를 탐지하고
운영자가 읽을 수 있는 문장으로 설명합니다.

| 단계  | 구현 내용                                           | 확인 화면     |
| ----- | --------------------------------------------------- | ------------- |
| 1단계 | 공공 Open API 2종 연동, 서버 프록시, 예외 처리      | `/stage1`     |
| 2단계 | 공통 SensorData 구조로 표준화                       | `/stage2`     |
| 3단계 | 설비 5종 3D 표현, 센서 연동, 상태 시각화            | `/`           |
| 4단계 | 이상탐지 3종, 근거·원인 표시, 운영자 문장 자동 생성 | `/` 우측 패널 |

**대상 시설**: 울산 OO배수지 (가상 시설, 실제 배수지 표준 구성 기준)

**설비 구성**: 정수 저수조, 1호 가압펌프, 유출 제어밸브, 유입 관로, 전처리 여과설비

## 2. 사용 기술

| 구분       | 기술                           | 선택 이유                                        |
| ---------- | ------------------------------ | ------------------------------------------------ |
| 백엔드     | Node.js, Express               | API 프록시와 정적 파일 서빙을 단일 서비스로 구성 |
| 프론트엔드 | Vue.js (Composition API), Vite | 컴포넌트 단위 상태 관리, 개발 서버 프록시 내장   |
| 3D         | Three.js r169                  | WebGL 사용                                       |
| 라우팅     | Vue Router                     | 단계별 화면 분리                                 |
| 환경변수   | dotenv                         | 인증키 분리                                      |

**기술 스택 선정 근거**

주력 스택은 Java/Spring Boot이나, 본 과제는 브라우저 3D 렌더링과 실시간 화면
갱신이 핵심이라 프론트엔드 비중이 큽니다. Three.js 연동과 단일 서비스 배포를
고려해 Node.js + Vue.js를 선택했습니다.

다만 서버 구조는 Spring에서 사용하던 계층 분리를 그대로 적용했습니다.
어댑터 규약과 구현체 분리, Controller–Service 역할 분담, DTO 검증 계층이
각각 `adapters/`, `routes/`↔`lib/`, `validateSensorData()`에 대응합니다.
인터페이스를 정의하여 TypeScript로 작성하려했으나 JSDoc과 런타임 검증을 활용하여 JavaScript로 작성하였습니다.

**Three.js**: TresJS 같은 Vue 래퍼를 쓰지 않았습니다.
의존성이 하나 줄고, 씬 생성부터 GPU 리소스 정리까지 흐름이 한 파일에 드러나 읽고 설명하기 쉽기 때문입니다.

## 5. 실행 방법

```bash
npm run dev       # 개발 모드 → http://localhost:5173
```

Express(4000)와 Vite(5173)를 동시에 띄웁니다. 개발 중에는 Vite가 `/api` 요청을
Express로 넘기고, 운영에서는 Express가 빌드된 읽어옴으로 CORS 설정이 필요 없습니다.

```bash
npm run build && npm start   # 운영 모드 → http://localhost:4000
npm run verify               # 인증키 없이 변환·탐지 로직만 검증
npm run samples              # 실제 API 응답을 samples/에 저장
npm run csv                  # 표준화 결과를 CSV로 내보내기
npm run model                # 3D 설비를 glTF 2.0으로 내보내기
```

| 경로          | 내용                                                |
| ------------- | --------------------------------------------------- |
| `/`           | 3D 트윈 + 이상징후 분석                             |
| `/stage1`     | 원본 API 응답, 출처·호출시각, 실패 처리             |
| `/stage2`     | 원본 → SensorData 변환 대조, 제외 데이터, 매핑 근거 |
| `/api/health` | 인증키 설정 여부 확인                               |

## 7. 공공데이터 Open API 연동

### 연동한 API

| API                    | 제공 기관    | 엔드포인트                                               |
| ---------------------- | ------------ | -------------------------------------------------------- |
| 초단기실황조회         | 기상청       | `/1360000/VilageFcstInfoService_2.0/getUltraSrtNcst`     |
| 시도별 실시간 측정정보 | 한국환경공단 | `/B552584/ArpltnInforInqireSvc/getCtprvnRltmMesureDnsty` |

수집 항목: 기온(T1H), 습도(REH), 1시간 강수량(RN1), 풍속(WSD), PM10, PM2.5

### 호출 구조

```
브라우저 -> Express 프록시 -> 공공데이터포털
```

| 라우트                  | 역할                                   |
| ----------------------- | -------------------------------------- |
| `GET /api/raw/:source`  | 원본 응답 그대로 반환 (1단계 확인용)   |
| `GET /api/sensors`      | 표준화 + 탐지 + 보고문                 |
| `GET /api/sensors/meta` | 설비 목록, 매핑 근거, 임계값, 시나리오 |

### base_time 계산

기상청 초단기실황은 매시 30분에 생성되어 40분부터 제공됩니다.
현재 시각이 40분 이전이면 한 시간 전 정시를 사용합니다.
배포 환경은 대부분 UTC로 동작하므로 서버 로컬시각을 쓰면 KST와 9시간이
어긋납니다. `server/lib/time.js`에서 KST를 명시적으로 계산합니다.

### 예외 처리

| 오류 유형 | 상황                  | 처리                                    |
| --------- | --------------------- | --------------------------------------- |
| `timeout` | 5초 초과              | 지수 백오프 재시도 (300ms → 600ms, 2회) |
| `network` | 연결 실패             | 재시도                                  |
| `http`    | 4xx/5xx               | 재시도                                  |
| `format`  | JSON 대신 XML 수신    | **즉시 중단**                           |
| `service` | `resultCode !== '00'` | **즉시 중단**                           |
| `config`  | 인증키 미설정         | **즉시 중단**                           |

**재시도 정책**: 인증키 오류와 서비스 오류는 몇 번을 다시 불러도 결과가 같으므로
재시도하지 않습니다. 일일 호출 한도를 낭비하지 않기 위한 판단입니다.

**XML 오류 응답**: 공공데이터포털은 인증키가 등록되지 않았을 때
`dataType=JSON`으로 요청해도 200 OK와 함께 XML을 반환합니다.
Content-Type 헤더를 믿지 않고 본문 첫 글자를 검사해 판별합니다.

**부분 실패 허용**: 한 출처가 실패해도 전체를 오류로 떨구지 않습니다.
기상청이 죽어도 에어코리아 값으로 화면 일부는 살아 있어야 운영 화면으로서
의미가 있기 때문입니다. 실패 내역은 응답의 `sources[]`에 담아 화면에 표시합니다.

### 데이터 출처와 호출 시각

성공·실패 여부와 무관하게 응답에 출처명, 출처 URL, 호출 시각을 포함합니다.
`SensorData`에는 원 데이터의 관측 시각(`timestamp`)과 서버 호출 시각
(`collectedAt`)을 분리해 담아 추적이 가능합니다.

## 8. 데이터 표준화 방법

### SensorData 인터페이스

```ts
interface SensorData {
  timestamp: string; // ISO 8601, KST 오프셋 포함
  sensorId: string; // 'TANK-01-WATER_TEMP'
  sensorName: string; // '저수조 수온'
  sensorType: string; // 'temperature'
  value: number;
  unit: string; // '℃'
  location: string; // '울산 OO배수지 · 정수 저수조'
  status: "normal" | "warning" | "danger";
  isAnomaly: boolean;
  source: string; // '기상청 초단기실황'
}
```

추적성과 3D 연동을 위해 확장 필드 5개를 추가로 포함합니다.
`equipmentId`(3D 객체 연결), `collectedAt`(호출 시각), `sourceUrl`,
`originCode`(변환 전 코드), `originValue`(변환 전 값)

### 인터페이스 사용

JavaScript에는 TypeScript의 `interface`가 존재하지 않아 다음 두 가지로 인터페이스를 대처하였습니다.

1. **JSDoc `@typedef`** — 에디터 자동완성과 타입 힌트
2. **`validateSensorData()`** — 런타임에 필드 존재와 타입을 실제로 검증

필수 필드 누락, 타입 불일치, `timestamp` 형식 위반, `status`가 지정 3값을
벗어난 경우, `status`와 `isAnomaly`의 모순을 잡아냅니다.
어댑터가 규격을 어기면 화면에 도달하기 전에 서버 로그에 기록되고 제외됩니다.

### 타임스탬프 일관성

| 출처       | 원본 형식                                   | 변환 후                     |
| ---------- | ------------------------------------------- | --------------------------- |
| 기상청     | `baseDate: "20260806"` + `baseTime: "1400"` | `2026-08-06T14:00:00+09:00` |
| 에어코리아 | `dataTime: "2026-08-06 14:00"`              | `2026-08-06T14:00:00+09:00` |

에어코리아는 자정을 `24:00`으로 표기하는 경우가 있어 다음 날 `00:00`으로
보정합니다.

### 단위 일관성

각 센서 사양(`SensorSpec`)에 단위와 환산식을 명시하고, 어댑터가 아닌 공통
계층에서 일괄 적용합니다. 어댑터마다 환산 규칙이 갈리는 것을 막기 위해서입니다.

### 결측·중복·오류 응답 처리

과제 규격상 `value`가 `number`(널 불가)이므로, 처리할 수 없는 데이터는
`SensorData` 배열에 넣지 않고 `rejected` 배열로 분리해 사유와 함께
반환합니다. 규격을 지키면서 결측·중복 처리 요구사항도 충족하는 방식입니다.

| 사유           | 판정 기준                                              |
| -------------- | ------------------------------------------------------ |
| `missing`      | 기상청 `-99`/`-998`/`-999`, 에어코리아 `"-"`/빈 문자열 |
| `duplicated`   | 같은 `sensorId`가 두 번 수신 — 최초 값만 채택          |
| `out_of_range` | 환산 결과가 유한한 수가 아님                           |

결측 판정은 `parseValue()` 한 곳에 모여 있습니다.
에어코리아는 울산 내 다수 측정소를 반환하므로 `stationName` 기준으로 중복을
제거한 뒤 대표 측정소를 선정합니다. **PM10 유효값을 가진 첫 측정소**를
채택했습니다. 평균을 쓰면 고장 측정소의 이상값에 끌려가기 때문입니다.

### 변환 로직의 재사용 가능한 구조

새 API를 추가할 때는 아래 형태의 객체 하나만 만들면 됩니다.

```js
{
  (id, name, sourceUrl, fetchRaw(), toSensorData(raw, collectedAt));
}
```

어댑터는 API마다 다른 '읽어오기'와 '항목 추출'만 담당하고, 결측 판정·단위
환산·상태 판정은 `buildSensorData()`가 전담합니다.

| AIRKOREA PM10 | 전처리 여과설비 | 부하율      | `25+PM×0.6`  | 미세먼지가 흡기 필터 폐색에 직접 영향 |

상세 근거와 임계값은 `/stage2` 화면 및 `server/lib/plant.js`의 `rationale`
필드에 기록했습니다.

**실제 현장 적용 시**: `plant.js`의 매핑 계층만 SCADA 태그로 교체하면
표준화·3D·이상탐지 로직은 변경할 필요가 없습니다. 이 분리가 설계의 핵심입니다.

### 사용한 모델 파일 및 출처

외부에서 내려받은 3D 모델을 사용하지 않았습니다. 모든 설비 형상은
Three.js 기본 지오메트리(`CylinderGeometry`, `BoxGeometry`, `SphereGeometry`,
`TorusGeometry`, `RingGeometry`)를 조합해 코드로 생성했습니다.
따라서 **모델 원본은 `client/src/components/TwinScene.vue` 소스코드 자체**입니다.

제출 규격이 GLB·GLTF·FBX·OBJ·BLEND 중 하나를 요구하므로, 동일 지오메트리를
glTF 2.0으로 내보내 **`models/ulsan-reservoir-equipment.gltf`** 로 포함했습니다
(설비 5종, 메시 25개, 재질 25개). `npm run model` 로 재생성할 수 있습니다.
3D 화면 우측 하단의 «3D 모델 glTF로 내보내기» 버튼으로도 현재 씬을
내려받을 수 있습니다.

프로토타입 단계에서 형상 정확도보다 **식별 가능성**을 우선했습니다.
실제 적용 시에는 설비 제조사 도면 기반 glTF 모델로 교체하는 것이 적절합니다.

### 카메라 조작

`OrbitControls`로 구현했습니다.

| 동작      | 조작                       |
| --------- | -------------------------- |
| 회전      | 좌클릭 드래그              |
| 확대·축소 | 마우스 휠 (거리 5~34 제한) |
| 이동      | 우클릭 드래그              |

바닥 아래로 내려가지 않도록 `maxPolarAngle`을 제한했습니다.

### 객체 선택

`Raycaster`로 클릭 지점에 광선을 쏴 맞은 메시를 찾고, 부모를 거슬러 올라가며
`userData.equipmentId`를 탐색합니다. 설비가 여러 메시로 구성되어 있어 어느
부분을 클릭해도 같은 설비로 인식됩니다. 빈 공간을 클릭하면 선택이 해제됩니다.

선택된 설비는 바닥에 청색 링이 표시되고, 우측 패널에 설비명·ID·설명과
소속 센서의 값·단위·상태가 나타납니다.

### 상태 시각 구분

| 상태   | 색상           | 조건                  |
| ------ | -------------- | --------------------- |
| 정상   | 녹색 `#2fb96a` | 임계값 내             |
| 주의   | 황색 `#eaa010` | 주의 임계값 초과/미달 |
| 위험   | 적색 `#e5484d` | 위험 임계값 초과/미달 |
| 미수신 | 회색 `#5c7383` | 데이터 없음           |

설비별 대표 상태는 **소속 센서 중 가장 심각한 상태**입니다.

**바닥 상태 링**: 본체 색만으로는 카메라 각도에 따라 설비가 서로 가려 상태를
놓칠 수 있습니다. 어느 각도에서도 판독되도록 바닥에 상태색 링을 깔았습니다.
위험 상태의 링만 맥동시켜 시선을 유도합니다.

**실시간 연동**: 60초 주기로 `/api/sensors`를 호출하고, 상태가 바뀌면 Vue의
`watch`가 3D 씬의 재질 색상을 갱신합니다. 씬을 다시 만들지 않습니다.

### 성능 처리

Three.js가 번들의 대부분(500kB)을 차지하므로 `defineAsyncComponent`로
분리했습니다. 1·2단계 화면에서는 내려받지 않습니다. 초기 번들 609kB → 114kB.

`onBeforeUnmount`에서 geometry·material·renderer를 순회하며 `dispose()`
합니다. Three.js는 GC가 GPU 리소스를 회수하지 않아 화면을 오갈 때마다
메모리가 누적되기 때문입니다.

## 10. 이상징후 판단 방법

### 적용한 탐지 방법 (3종)

| 방법        | 판정 기준                                         | 필요 표본 |
| ----------- | ------------------------------------------------- | --------- |
| **임계값**  | 센서별 4단계 임계값(위험↓/주의↓/주의↑/위험↑) 대비 | 1개       |
| **Z-score** | 이력 평균 대비 \|Z\| ≥ 2.5 주의, ≥ 3.0 위험       | 5개       |
| **변화율**  | 직전 값 대비 ≥ 25% 주의, ≥ 40% 위험               | 2개       |

### 임계 기준

| 센서             | 위험↓ | 주의↓ | 주의↑ | 위험↑ | 단위 | 근거                            |
| ---------------- | ----- | ----- | ----- | ----- | ---- | ------------------------------- |
| 저수조 수온      | 2     | 4     | 22    | 25    | ℃    | 동절기 동결, 하절기 미생물 번식 |
| 저수조 수위      | 25    | 40    | 90    | 95    | %    | 펌프 공회전, 월류 위험          |
| 펌프 베어링 온도 | —     | —     | 55    | 65    | ℃    | 그리스 열화, 제조사 경보 기준   |
| 펌프실 습도      | —     | —     | 80    | 90    | %    | 결로에 의한 전동기 절연저하     |
| 유입 유량        | 30    | 60    | 200   | 240   | ㎥/h | 관로 설계유량                   |
| 밸브 차압        | 0.8   | 1.2   | 3.0   | 3.5   | bar  | 표준 운전압, 수격 위험          |
| 여과설비 부하율  | —     | —     | 70    | 85    | %    | 교체 권고, 즉시 교체            |

### 이력 확보

공공 API는 단일 시점 스냅샷만 제공하므로 서버 메모리에 센서별 최근 30개 값을
누적합니다. 같은 관측시각이 반복 조회되면 이력이 오염되므로 직전 값과 동일하면
넣지 않습니다.

**Z-score 표준편차 하한**: 값이 거의 변하지 않는 센서는 표준편차가 0에
수렴해 Z-score가 50을 넘는 값이 나옵니다. 정상 변동도 이상으로 잡히므로
평균의 2% 또는 0.05 중 큰 값을 하한으로 적용했습니다.

### 판단 근거와 원인 표시

탐지마다 숫자가 포함된 근거 문장과 설비별 추정 원인을 함께 생성합니다.

```
[임계값 판정] 측정값 27.6℃가 위험 기준 25℃를 초과했습니다.
[통계적 이탈(Z-score)] 최근 6회 관측 평균 51.8℃, 표준편차 1.04 대비
                        Z=7.68로 통계적 이탈 범위입니다.
[변화율 감시] 직전 관측 46%에서 현재 95.8%로 108.3% 급변했습니다.
```

### 운영자용 분석 문장 자동 생성

설비 단위로 묶어 **상황 → 원인 → 종합** 순으로 서술합니다.
운영자는 센서가 아니라 설비 단위로 조치하기 때문입니다.

> 정수 저수조의 저수조 수온이 27.6℃로 위험 상태입니다. 수온 상승은 외기온
> 상승과 체류시간 증가가 겹칠 때 발생합니다. 잔류염소 소모가 빨라져 수질
> 저하로 이어집니다. 동일 설비에서 2건의 이상이 동시에 탐지되었습니다.
> 단일 센서 오류보다 설비 상태 변화일 가능성이 높습니다.

**LLM 대신 규칙 기반 템플릿을 채택한 이유**

1. 동일 입력에 동일 출력이 보장되어 시연과 검증이 가능합니다
2. 근거 숫자가 문장에 그대로 반영되므로 환각이 발생하지 않습니다
3. 외부 API 지연 없이 즉시 생성됩니다

상용 확장 시에는 이 문장을 LLM 프롬프트의 **근거 블록**으로 전달하는 방식이
적합하다고 판단했습니다. LLM에 판단을 맡기지 않고 표현만 맡기는 구조입니다.

한글 조사는 유니코드 종성 인덱스(`(코드 - 0xAC00) % 28`)로 받침을 판별해
확정합니다. `수온이(가)` 같은 표기가 나오면 제어실 게시 문서로 쓸 수 없기
때문입니다.

### 권장 점검사항

센서별 점검 항목에 더해, 적용된 탐지 방법에 따라 계측 계통 점검 항목을
추가합니다. 변화율 탐지가 포함되면 신호선·변환기 확인을, Z-score 탐지가
포함되면 센서 교정 이력 확인을 덧붙입니다.

예시 — 1호 가압펌프 베어링 온도 위험:

1. 베어링 그리스 주입 상태 및 최종 주입일 확인
2. 펌프-전동기 축 정렬(얼라인먼트) 점검
3. 흡입측 스트레이너 차압 확인 (공동현상 여부)
4. 운전전류 측정 후 정격 대비 비교
5. 센서 교정 이력 확인 및 드리프트 여부 판단 (통계적 이탈 이력 있음)

### 이상 상황 재현 시나리오

실제 울산 기상은 대부분 정상 범위라 평가 시점에 경보 화면을 못 볼 수 있습니다.
임계값을 임시로 낮추는 방법은 판정 기준 자체가 바뀌어 근거 문장의 숫자가 실제
운전 기준과 달라지므로 채택하지 않았습니다.

대신 실제 API 값을 그대로 가져오되 지정 센서의 값만 덮어써, 임계값·탐지
로직·문장 생성은 운영과 완전히 동일하게 동작시킵니다.
재현 중임은 응답의 `scenario` 필드와 화면 배너로 명시합니다.

| 시나리오           | 재현 상황                                           | 호출                   |
| ------------------ | --------------------------------------------------- | ---------------------- |
| 혹서기 수온 상승   | 외기온 급등으로 저수조 수온과 베어링 온도 동반 상승 | `?scenario=heatwave`   |
| 집중호우 유입 급증 | 단시간 강우로 유입 유량과 수위 동시 상승            | `?scenario=heavy_rain` |
| 고농도 미세먼지    | PM10 급증으로 흡기 필터 폐색 진행                   | `?scenario=dust_storm` |
| 저수위 경보        | 상류 취수 중단으로 유입 차단, 저수위 형성           | `?scenario=low_water`  |

3D 화면 상단 버튼으로 전환할 수 있습니다.

## 11. AI·AX 활용 내역

### AI 사용 범위

| 구분                    | 내용                                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| 사용 도구               | Claude Opus 5(effort:max)                                                                      |
| AI가 초안을 생성한 부분 | 프로젝트 구조, 어댑터 규약 골격, Three.js 지오메트리 구성, CSS 토큰                            |
| 직접 작성·결정한 부분   | 기술 스택 선정, 설비 구성과 매핑 정책, 임계값, 점검 항목, 대표 측정소 선정 기준, 재현 시나리오 |
| AI를 쓰지 않은 부분     | 인증키 발급, 실제 API 응답 확인, 화면 캡처, 시연 영상                                          |

### 검증 과정에서 발견해 수정한 사항

**① SensorData 규격 불일치** — 초안은 자체 정의한 필드명(`observedAt`, `label`,
`type`)을 사용했고 `location`·`isAnomaly`가 없었으며 상태값이 `critical`이었습니다.
과제 지정 규격(`timestamp`, `sensorName`, `sensorType`, `location`, `isAnomaly`,
`status: "danger"`)에 맞춰 전면 수정하고, 런타임 검증 함수도 지정 필드 기준으로
다시 작성했습니다.

**② `value: number` 규격과 결측 처리의 충돌** — 초안은 결측 시 `value: null`을
넣었으나 규격상 `value`는 널을 허용하지 않습니다. 결측·중복·범위이탈 데이터를
`rejected` 배열로 분리하는 구조로 변경했습니다.

**③ 한국어 조사 미처리** — 자동 생성 문장에 `수온이(가)`, `기준을(를)` 형태가
그대로 출력되었습니다. 유니코드 종성 인덱스로 받침을 판별하는
`server/lib/korean.js`를 작성해 조사를 확정하도록 수정했습니다.

**④ 설비명 중복 출력** — `정수 저수조의 저수조 수온이 … 정수 저수조 수온 상승은`
처럼 설비명이 한 문장에 두 번 나왔습니다. 원인 문구 테이블에서 설비명 접두사를
제거했습니다.

**⑤ Z-score 폭주로 인한 오탐** — 값이 거의 변하지 않는 센서는 표준편차가 0에
수렴해 Z-score가 50을 넘었습니다. 표준편차 하한을 적용했습니다.

**⑥ 배포 환경 시각 오류** — 초안은 서버 로컬시각으로 기상청 `base_time`을
계산했습니다. 배포 환경은 UTC로 동작하므로 KST와 9시간이 어긋나 조회가
실패합니다. KST를 명시적으로 계산하도록 수정했습니다.

**⑦ 재시도 정책 조정** — 초안은 모든 오류를 재시도했습니다. 인증키 오류는
재시도해도 결과가 같아 호출 한도만 소모하므로 타임아웃·네트워크 오류에만
적용하도록 변경했습니다.

**⑧ 인증키 인코딩 문제** — 인코딩 키를 `URLSearchParams`에 넣으면 이중
인코딩되어 인증에 실패합니다. 디코딩 키 사용을 확정하고 `.env`에
명시했습니다.

**⑨ 초기 번들 과대** — Three.js가 포함되어 첫 화면 로드에 609kB를 내려받았습니다.
`defineAsyncComponent`로 분리해 114kB로 줄였습니다.

**⑩ Three.js 리소스 누수** — 컴포넌트 언마운트 시 정리가 없어 화면을 오갈 때마다
GPU 메모리가 누적되었습니다. `dispose()` 처리를 추가했습니다.

**⑪ 에어코리아 엔드포인트 오류** — 초안은 서비스명을 `ArpltnInqirySvc`로
작성했습니다. 실제 호출 시 인증키가 정상인데도 `NO_OPENAPI_SERVICE_ERROR`(코드 12)가
반환되어, 공공데이터포털 문서를 대조해 `ArpltnInforInqireSvc`가 정확한 경로임을
확인하고 수정했습니다. 함께 프로토콜도 `http`에서 `https`로 통일했습니다.
AI 초안을 실제 API에 연결해 보지 않았다면 발견할 수 없는 오류였습니다.

## 13. 미구현 사항 및 한계

**1. 밸브 차압 매핑의 물리적 근거가 약합니다.**
풍속을 차압 변동 인자로 사용한 것은 시뮬레이션 목적이며 실제 상관관계는
없습니다. 7개 매핑 중 가장 먼저 실제 센서로 교체해야 할 항목입니다.
코드 주석과 `/stage2` 화면에도 명시했습니다.

**2. 이력이 서버 메모리에만 있습니다.**
프로세스가 재시작되면 Z-score 기준이 초기화됩니다. 운영 적용 시 시계열
DB(InfluxDB, TimescaleDB)가 필요합니다.

**3. 설비 형상이 실제 도면과 다릅니다.**
식별 가능성을 우선한 단순 지오메트리입니다. 실제 적용 시 제조사 도면 기반
glTF 모델로 교체해야 합니다.

**4. 센서값이 실측이 아닌 환산값입니다.**
공공 API가 배수지 내부 센서를 제공하지 않아 기상·대기질 관측값을 환산했습니다.
매핑 계층만 SCADA 태그로 교체하면 나머지 로직은 그대로 사용 가능합니다.

**5. 단일 배수지만 다룹니다.**
다중 시설 확장 시 `plant.js`를 시설별 설정으로 분리해야 합니다.

**6. 인증·권한 기능이 없습니다.**
프로토타입 범위에서 제외했습니다.

**7. 이상 이력 조회 기능이 없습니다.**
현재 시점의 탐지 결과만 표시하며 과거 경보 목록은 남지 않습니다.

**8. 도메인 지식의 한계 및 AI의존성**
관련 도메인 지식, 계측기준, 실제 사용하는 장비, 새로 사용해보는 WebGL 등 전혀 알지 못했던 지식을 활용해 프로토타입
프로젝트를 직접 구현하는데 있어서 찾아보며 검증하기까지 과정이 오래걸렸으며, 전체적인 이해도가 낮아 구현하기 어려웠습니다.
그런 와중 도메인 지식과 프로젝트의 코드작성에 생성형AI의 도움을 많이 받았습니다.
